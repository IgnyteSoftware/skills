# Triage

Read the item, discussion, existing labels, PR diff when applicable, and relevant implementation. Use project conventions; consult project-setup only if a needed mapping is unresolved. Check for duplicates, already-implemented behavior, and prior rejection decisions before proposing new work.

Verify a reported defect or PR claim where practical and state uncertainty otherwise. Recommend the appropriate state, priority, missing information, and next action. Use grilling for unresolved product decisions, not facts you can inspect.

For work ready to implement, provide a brief with current and desired behavior, acceptance criteria, scope, and blockers. For an existing PR, describe what remains to fix. Preserve attribution policy; do not add agent signatures or AI disclaimers.

Change labels, comment, or close items only within the user's authorized triage scope. Record a durable rejection in the repository's existing decision history when appropriate; an already-built feature is not a rejected one. Finish with decisions, evidence, and any tracker changes made.
